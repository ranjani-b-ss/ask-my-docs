## S14 — the claimant-text redactor corrupted identifiers, amounts and ordinary words in the logs
- Found 2026-10-09 when `eval/rescore_capstone.py` crashed with `KeyError: 'cap_cf442790a57f'`: the host trace file stored that id as `cap_cf[REDACTED]a57f`. Two of 36 eval traces (CLM-2026-00601, -00608) could no longer be found or stitched by their own id; server spans carried the same corrupted ids (11 rows).
- Cause: the PIN-code pattern added for S8 matched any six-digit run — inside hex ids, inside `"amount":600000.0`, after "INR"/"limit" — and the address cue matched the English verb "address", so "…to address the adjuster's question" lost the rest of the sentence.
- Collateral over-redaction in the v1 logs (not a PII leak, a loss of fidelity): ~25 occurrences of model reasoning cut after the verb "address"; policy limits and sub-limit values replaced by `[REDACTED]` in 4 rows; chunk-hash prefixes in `retrieved_context`. **Not restored** — the original text is gone; the v2 re-run regenerates every row with the fixed redactor.
- Fix: PIN now needs a standalone six-digit token after a Title-case place word; "address" is a cue only as `Address:` / `address is`; ids the system generates (`STRUCTURAL_KEYS` in `src/span_log.py`) bypass the scrubber entirely. 5 regression tests in `tests/test_redact_claimant.py`.
- Repaired by exact-string replacement, backups in `traces/pre_s14_backup/`: the two trace ids (true values taken from `eval/capstone_results_v1_raw.json`) and `REF-9F313323` (the only `REF-9F…` in `referrals.jsonl`).
- Status: fixed in code; v1 logs partially repaired (ids only); v2 logs clean.

## S15 — a run that never reaches lookup_policy ends with no referral at all
- Found 2026-10-09 while writing `10X_PLAN.md`. During the Gemini 429 outage, 10 of 10 affected v2 runs, covering 9 claims (00584 twice, 00601–00607, 00609) have **no row in `traces/referrals.jsonl`** and no `refer_to_adjuster` span; the eval's `referral_present` assertion failed on all of them.
- Cause: the invariant "every request ends in a referral" is guarded by `if state.referral is None and state.loss_date is not None` in `src/agent/triage_agent.py`. `loss_date` is set only by the `lookup_policy` result, and a dead provider never lets the model get there. The referral tool itself needs only the claim number.
- Also: each such claim waited its full 240 s wall budget on a provider that was failing on every call.
- Fix (2026-10-09): the backstop no longer requires a loss date — `if state.referral is None:` — because the referral tool needs only the claim number. Test: `tests/test_triage_provider_outage.py` (3 tests; written first and run red: `expected exactly one referral, got 0`, then green). It also pins that a provider dying *after* `lookup_policy` still yields exactly one referral, not two.
- Status: **fixed in code, verified against a stub provider only** — not re-run live (quota). The 10 outage runs in `traces/capstone_traces.jsonl` (label `capstone-eval-v2`, `usage.total_tokens == 0`) remain as the before-evidence. NOT fixed, deliberately: each dead-provider claim still waits its full 240 s (circuit breaker, `10X_PLAN.md` §3.1).

## S17 — a citation's clause label is the chunk's first heading, not where the cited fact lives

- Blind spot in S12: `wording_versions.superseded_by` and the `superseded_not_cited` assertion both read the clause number from the first heading, so a superseded clause held under an unamended heading (`PW-HEALTH-002::3`, `PW-CLAIMS-003::6`; 2 of 31 base chunks) is invisible to both. 6 of 72 packets cite one; reliance on the superseded text not shown. One chunk (`PW-HEALTH-002::2`) is over-marked in the other direction.
- Corrects an earlier claim in `WEAKNESSES.md`/`EVAL_REPORT.md` that CLM-2026-00606 cited an "irrelevant" clause: the chunk's second section states the tyre limit.
- **Endorsement-side half (found 2026-10-13 during the bonus):** the amendment map is built from each endorsement chunk's FIRST heading, so an amendment sitting under a later heading is invisible. Raw-corpus truth has 16 amended (document, clause) pairs; the index-derived map has 11. **Missed: `PW-MOTOR-001` clauses 4 (intimation) and 5, `PW-HEALTH-002` clauses 2 (pre/post-hospitalisation) and 8 (reimbursement), `PW-CLAIMS-003` clause 5 (on-account).** These are the clauses behind the two effective-day retrieval cases that stay red (motor intimation, motor reimbursement) and behind the v2 584 label-mismatch. (The `superseded_not_cited` assertion reads the raw corpus, so its map is complete; it still keys the CITED chunk by its first heading.)
- Status: **open** — found and measured, not fixed. Fix is small (parse every `Amendment to Clause X` heading in the chunk text, not just the section label) and has not been made.

## S22 — the parser rejects `ActionInput:` and the model sometimes writes it
- Found 2026-10-14 reading CLM-2026-00567 in the v3 run: 8 of 12 laps were `malformed` because the model wrote `ActionInput: {...}` (no space) where the loop expects `Action Input:`. It burned the 12-lap budget and the claim ended with an empty packet and no `get_limits` result. Malformed laps across the run: 13 in v3, 21 in v2 — the same family.
- Measured across every logged trace: **68 of the 72 malformed laps were this one variant** (capstone evals, the straddle ablation, the Week 11 arms); the other 4 are different problems (a bare JSON code block; turns with a thought and no action).
- Fix (2026-10-14, on request): `_find_json_object` (`src/agent/react_agent.py`, shared by the capstone, Week 9, Week 11 and workflow loops) matches its marker with optional spaces/tabs — `Action Input` also matches `ActionInput` — and never across a newline. Replaying the 72 logged malformed laps through the fixed parser: **68 now parse as actions, 4 still malformed.** 6 tests, one pinned to the real logged text of CLM-2026-00567's lap 4.
- Live check: CLM-2026-00567 re-run once under the otherwise identical system: **6 laps / 16,462 tokens / all assertions pass** (was 12 laps / 30,019 tokens / fail); one lap still wrote `ActionInput` and was accepted. n = 1 — v2 also passed this claim, so a single pass is not proof of a better system, only that the loop no longer dies on the spelling.
- **Not changed:** the error message for a missing marker is still empty (`Action Input did not parse: `), so a model that gets the format wrong in some *other* way still gets no hint what to fix; and `_HAS_FINAL` still requires the exact `Final Answer:` spelling. **Full 36-case re-run with the fix (v3b, 2026-10-14/18; first attempt stopped by the model quota after 10 claims, resumed for the other 26): 33/36 = 92%** (v3 before the fix 32/36). 00567, 00606 and 00607 now pass; 00468 and 00491 newly fail (a token-budget stop and S17 respectively) — net +1, within single-run noise.
